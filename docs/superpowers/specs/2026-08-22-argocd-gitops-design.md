# Sub-project 2: GitOps with ArgoCD — Design

**Status:** Approved for planning
**Depends on:** Sub-project 1 (cluster bootstrap), complete and verified.

## Goal

Bring up ArgoCD in App-of-Apps mode as the source of truth for the cluster,
migrating everything sub-project 1 installed via bash scripts (Cilium,
cert-manager, the ClusterIssuer, the shared Gateway, dnsmasq, the smoke-test
app) to be ArgoCD-managed `Application` resources sourced from this repo's
GitHub remote (`https://github.com/tilraunastofan/kind-lab`, private).
`task cluster:up` ends with ArgoCD itself reachable and verified over trusted
HTTPS at `https://argocd.lab.test`, the same bar sub-project 1 met with the
nginx smoke test.

## Why migrate existing script-installed components into ArgoCD?

The README states ArgoCD should manage "all charts and apps" via App-of-Apps.
Leaving Cilium/cert-manager/gateway/DNS permanently script-only would mean two
parallel deployment mechanisms indefinitely, and every future sub-project
would need to decide which one to use. Migrating now, while there's only one
sub-project's worth of components, is cheaper than migrating later.

## The chicken-and-egg problem

ArgoCD's own pods need a working CNI to schedule, so Cilium cannot be
installed *by* ArgoCD from a cold cluster. The design keeps a minimal
script-driven "layer 0" — just enough for ArgoCD to exist and reach Git — and
hands everything else to ArgoCD:

- **Script-only, permanent (layer 0):** step-ca, cloud-provider-kind, kind
  cluster creation, Cilium Helm install, Gateway API CRDs, ArgoCD's own Helm
  install, the Git deploy key, and the root App-of-Apps `Application`.
- **ArgoCD-managed from here on:** cert-manager, the step-ca ClusterIssuer,
  the shared Gateway (listeners chart), dnsmasq/DNS, the smoke-test app, and
  ArgoCD's own Helm release (adopted after bootstrap — self-referential, a
  standard ArgoCD pattern).

Cilium and the Gateway CRDs stay script-managed permanently — they're the
true bootstrap layer and change rarely; migrating them buys nothing and adds
risk (ArgoCD reconciling the CNI it's running on).

**Adoption, not reinstall:** for each existing component, the ArgoCD
`Application` targets the same Helm release name/namespace the script already
created. ArgoCD's next sync reconciles the existing release in place —
no resource churn, no downtime.

## Repo layout

```
helm/
  argocd/                  # values.yaml for the upstream argo-cd chart
  cilium/                  # unchanged, script-managed
  cert-manager/            # unchanged content, now also an Application source
  cluster-issuer/          # unchanged content, now also an Application source
  gateway/                 # rewritten as a real chart (see below)
  dns/                     # unchanged content, now also an Application source
  smoke-test/              # gateway-listeners.yaml removed (see below)
gitops/
  root-app.yaml            # the one Application bootstrap.sh applies directly
  apps/
    cilium.yaml             # NOT included — Cilium stays script-only
    cert-manager.yaml
    cluster-issuer.yaml
    gateway.yaml
    dns.yaml
    smoke-test.yaml
    argocd.yaml             # ArgoCD adopts its own Helm release
```

Each file under `gitops/apps/` is a standard ArgoCD `Application` pointing
`source.path` at the matching `helm/<name>` directory in this same repo, with
`syncPolicy.automated: {prune: true, selfHeal: true}`.

## Gateway listener scaling

`helm/gateway` becomes a templated chart instead of two files that each
replace `lab-gateway`'s whole `spec.listeners` array (the scaling problem
flagged in `CLAUDE.md`'s open decisions).

`values.yaml`:
```yaml
listeners:
  - name: smoke
    hostname: smoke.lab.test
    certificateRef: smoke-tls
  - name: argocd
    hostname: argocd.lab.test
    certificateRef: argocd-tls
```

`templates/gateway.yaml` loops over `.Values.listeners` and emits, per entry,
one `HTTP` listener and one `HTTPS` listener sharing the same `hostname` —
generically applying the workaround for the upstream Cilium bug
([cilium/cilium#44123](https://github.com/cilium/cilium/issues/44123)) that
silently drops routes through a wildcard HTTP listener once any HTTPS
listener on the same Gateway claims a specific hostname (see
`docs/superpowers/plans/2026-08-21-cluster-bootstrap.md` Task 7 and the prior
comment in `helm/smoke-test/gateway-listeners.yaml`).

Onboarding a new app's hostname = append one entry to
`helm/gateway/values.yaml` in a PR to this repo; ArgoCD reconciles the
Gateway automatically. `helm/smoke-test/gateway-listeners.yaml` is deleted —
its content is now generated by the gateway chart from the `smoke` entry
above.

Each `Certificate` (`smoke-tls`, `argocd-tls`) stays owned by its own app's
`helm/<app>` directory, as today — only the Gateway's listener array is
centralized.

## ArgoCD installation and Git access

`scripts/argocd-up.sh` (new, follows the existing script conventions —
sources `lib.sh`, `set -euo pipefail`, idempotent):

1. `helm upgrade --install argocd argo/argo-cd -n argocd --create-namespace -f helm/argocd/values.yaml`, wait for `argocd-server` ready.
2. Generate an ed25519 SSH deploy key at a fixed local path if one doesn't already exist (`~/.ssh/kind-lab-argocd-deploy` or repo-local equivalent — exact path decided during implementation).
3. Register it on the GitHub repo: `gh repo deploy-key add <pubkey path> --repo tilraunastofan/kind-lab --title kind-lab-argocd` (deploy keys are read-only by default; no-op if already registered).
4. Create/update the ArgoCD repository credentials Secret (`argocd.argoproj.io/secret-type: repo-creds`) from the private key, scoped to `https://github.com/tilraunastofan/kind-lab` — actually SSH URL (`git@github.com:tilraunastofan/kind-lab.git`) since the key is an SSH deploy key.
5. `kubectl apply -f gitops/root-app.yaml`.
6. `wait_for` all child Applications to report `sync.status: Synced` and `health.status: Healthy` via `kubectl get applications -n argocd -o json`.

No PAT, no manual GitHub UI step — the deploy key is read-only and scoped to
this one repo.

## ArgoCD UI exposure

`argocd-server` runs with `--insecure` (TLS termination handled by the
Gateway instead of ArgoCD's self-signed cert, same pattern as any other app
behind `lab-gateway`). `helm/argocd` gains a `Certificate` for `argocd-tls`
(issued by the step-ca ClusterIssuer, same as `smoke-tls`) and an
`HTTPRoute` with `parentRefs` pointing at the `lab-gateway`'s `argocd` listener
pair, `hostnames: [argocd.lab.test]`, backend `argocd-server:80`.

Login: default `admin` user, initial password read from the
`argocd-initial-admin-secret` ArgoCD creates automatically — no change to
that default flow, just documented in `README.md`'s troubleshooting section
alongside the existing `cloud-provider-kind` note.

## Updated bootstrap flow

`bootstrap.sh` sequence (script steps in **bold** are new or changed):

1. step-ca bootstrap (unchanged)
2. cloud-provider-kind bootstrap (unchanged)
3. kind cluster up (unchanged)
4. Cilium + Gateway API CRDs (unchanged, still script-only)
5. **`argocd-up.sh`** (new — replaces the direct `cert-manager-up.sh` /
   `issuer-up.sh` / `dns-bootstrap.sh` / gateway-apply / smoke-test steps,
   which become ArgoCD Applications instead of script steps)
6. **`smoke-test.sh`** becomes the ArgoCD-health check described above —
   waits for all Applications `Synced`+`Healthy`, then curls
   `https://argocd.lab.test` and asserts `200`.

`scripts/cert-manager-up.sh`, `scripts/issuer-up.sh`, `scripts/dns-bootstrap.sh`
are deleted — their one-time imperative logic is replaced by the
corresponding `gitops/apps/*.yaml` Applications, which ArgoCD reconciles
continuously instead of applying once.

`task cluster:down` and `task cluster:status` are updated to account for the
`argocd` namespace and to report Application sync/health status
respectively.

## Testing / verification

Same bar as sub-project 1: a full `task cluster:down` + `task cluster:up`
teardown/rebuild must succeed unattended (module the documented first-run
`sudo` steps) and end with:

- All `gitops/apps/*.yaml` Applications `Synced` and `Healthy`.
- `curl https://argocd.lab.test` returns `200` with a cert chain trusted by
  the macOS system store (verified via `curl -v`, `subject`/`issuer` lines
  showing the step-ca intermediate, same check used for `smoke.lab.test`).
- `smoke.lab.test` still resolves and serves `200` over HTTPS (regression
  check — proves the gateway chart's generated listeners still work
  correctly for a pre-existing hostname after the refactor).

## Out of scope (deferred to later sub-projects)

- Kargo, promotion pipelines, Forgejo — untouched by this design.
- Datadog Operator — untouched.
- Any change to how `demo-apps/` or Clickhouse get built — this sub-project
  only establishes the GitOps mechanism, not new workloads.
