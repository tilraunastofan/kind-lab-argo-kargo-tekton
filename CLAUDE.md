Bugs 2-4's fixes are idempotent and wired into `bootstrap.sh` (`pac-forgejo-trust-up.sh`, `pac-ca-trust-up.sh`); bug 1's fix (`pac-lan-forward-up.sh`) is standalone and run by hand, not wired into `bootstrap.sh` — but it is NOT a run-once-ever step: the LaunchDaemon itself persists across reboots, but its forwarding target (ingress-nginx's `cloud-provider-kind` LoadBalancer IP) is reassigned on every cluster rebuild, so the script must be re-run after every `cluster:up` (or any other event that changes that IP or the Mac's LAN IP) for LAN-delivered webhooks to keep reaching the cluster. One remaining fragility: mid-troubleshooting, the Raspberry Pi's Forgejo container was switched from dynamic to static Docker port publishing (`-p 3000:3000 -p 2222:22`) so it would stop breaking the user's own Caddy reverse-proxy config on every container recreation — a necessary fix, but now a fact about the Pi's setup that this repo doesn't manage (it only reaches the Pi via SSH for the two `pac-*-trust-up.sh` scripts). `.github/workflows/ci.yml` and the Kargo promotion sub-project's decision against using Forgejo for promotion approval are both untouched by this work.

**Full end-to-end verification of the simplified cluster** (2026-09-12) is complete and passing, to the same bar every sub-project above was held to: a real `task cluster:down` against the original `kind-lab` cluster, followed by a cold `task cluster:up` of `tekton-lab`, ending with every ArgoCD Application `Synced`/`Healthy`; all five hostnames (`argocd`, `headlamp`, `event-generator`, `smoke`, `pipelines-as-code`, all `*.tekton-lab.test`) served over trusted HTTPS; a real `git push` → Forgejo pull-mirror → PAC webhook → `PipelineRun` cycle reaching `Succeeded` with the commit status posted back to Forgejo; and Kargo's control plane (API, controller, webhooks, Project, Warehouse) healthy and running. Six real, previously-undiscovered bugs surfaced along the way — none caught by static review, all only reachable by actually running the renamed repo's bootstrap against a live GitHub/ArgoCD/Forgejo/Docker round-trip:

1. `scripts/argocd-up.sh`/`scripts/kargo-deploy-key-up.sh` had a bare `REPO_SLUG="tilraunastofan/kind-lab"` (no `.git` suffix), missed by every rename pass — ArgoCD's SSH clone had no read access to the actual repo.
2. Fixing (1) alone hit GitHub's account-wide deploy-key uniqueness constraint (`HTTP 422: key is already in use`) — both scripts reused the original `kind-lab`'s exact SSH keypairs. Gave this repo its own (`~/.ssh/kind-lab-argo-kargo-tekton-{kargo,argocd-deploy}`).
3. `gitops/apps/tekton-pipelines.yaml`/`pipelines-as-code.yaml` explicitly set `directory.recurse: false` (the field's own default); ArgoCD's own `Application` struct tags that field `omitempty`, so the live object silently drops the explicit `false` on write — the parent `root-app` never converged (`OutOfSync` forever) diffing its own children. Removed the redundant explicit value.
4. The renamed GHCR path never had any images pushed to it — Task 1 renamed the config, not the artifact. Built and pushed a fresh image (`scripts/build-and-push.sh`) and repointed both `helm/event-generator/values*.yaml`.
5. `helm/dns/templates/dnsmasq.yaml` hardcoded `address=/lab.test/...` — a slash-delimited domain string with no leading dot, so the `\.lab\.test` rename regex never matched it. dnsmasq answered `REFUSED` for every `*.tekton-lab.test` query.
6. `scripts/pac-lan-forward-up.sh`'s `PLIST_LABEL` was still `com.kind-lab.pac-lan-forward`, identical to the original repo's LaunchDaemon — its still-running, now-stale forwarder (bound to the Mac's real LAN IP, pointed at a torn-down cluster's dead Gateway IP) was found squatting on host port 443, blocking Docker/OrbStack from cleanly binding the new cluster's ingress-nginx LoadBalancer container. Renamed the label; the user unloaded the stale daemon (`sudo launchctl bootout`) and enabled passwordless `sudo` for this Mac going forward.
7. `scripts/pac-ca-trust-up.sh` built the PAC CA-trust bundle via `docker cp <container>:<path> -`, which streams a **tar archive** to stdout (not raw file bytes) — the ConfigMap ended up holding a tar-wrapped `ca-certificates.crt` that Go's `crypto/x509` (`SSL_CERT_FILE`) silently failed to parse, so the PAC controller/watcher kept failing outbound TLS to `git.local` with `x509: certificate signed by unknown authority` even though the correct root CA was technically present, buried in tar padding. Piped through `tar -xO` to unwrap it.

Also discovered along the way, informational only (no fix needed): `cloud-provider-kind` in this environment auto-provisions one synthetic per-namespace Gateway API `Gateway` (`kind-ingress-gateway`, `GatewayClass: cloud-provider-kind`) for every namespace holding an `Ingress` resource, each claiming its own IP from the same address pool `Service`-type `LoadBalancer`s draw from — after a `cloud-provider-kind` LaunchDaemon restart, these can transiently collide with a real Service's IP until the next reconcile. Not something this repo's manifests request or control; re-running `scripts/dns-bootstrap.sh` (or `task cluster:up`, which calls it) after any such restart re-points DNS at whatever IP ingress-nginx currently holds.

## Intent (from README.md)

This is a Kubernetes platform engineering lab built around a local `kind` cluster, managed via `task` (Taskfile.yaml) and bootstrap scripts (bash, invoked from the Taskfile).

- **Cluster**: `kind`; cluster infra images are `kind load`'ed, but demo-app images are pulled from a private `ghcr.io` registry (see Sub-project 3a below) — the local Docker registry container this line originally referred to was removed.
- **TLS**: cert-manager issues certs cluster-wide from an intermediate CA issued by a local `step ca` (already trusted by the macOS system trust store). Ingress is ingress-nginx, a plain Kubernetes Ingress controller, with cert-manager's ingress-shim solving ACME HTTP-01 challenges through it — traffic is real HTTPS end-to-end, not HTTP only.
- **GitOps**: ArgoCD, App-of-Apps pattern, manifests/charts sourced from this repo.
- **Promotion**: Kargo promotes a Go app release from dev to a "prod" lab environment, with a dashboard. A Git server with Actions (Forgejo, set up as a GitHub pull-mirror) is also in place — primarily to give Tekton Pipelines-as-Code a push source to react to (see Sub-project 5) rather than for promotion approval itself.
- **Observability**: Datadog Operator deploys the Cluster Agent. Uses the EU site (`https://app.datadoghq.eu`) and the local `DATADOG_API_KEY` env var — the cluster is free to use this key directly. A Datadog MCP server is also configured for Claude's own use (separate from the cluster's key).
- **Demo app**: a Go service generating continuous low-level dummy load, with high load triggerable via its web UI or API, writing data into Clickhouse.
- **Clickhouse**: vendored chart with a custom lab-scoped `values.yaml`.

## Open decisions

When working in this repo, be ready to advise on (not yet decided in README.md):

- Ingress controller: RESOLVED. Plain `ingress-nginx` (installed as an ArgoCD Application, `gitops/apps/ingress-nginx.yaml`), with each app declaring its own `Ingress` resource (`helm/*/extras/ingress.yaml`) instead of sharing a hand-rolled Gateway. This sidesteps the Cilium Gateway API hostname-isolation bug the original `kind-lab` had to work around (upstream [cilium/cilium#44123](https://github.com/cilium/cilium/issues/44123)) entirely — a plain Ingress controller doesn't have that shared-listener failure mode. `helm/*/extras/ingress.yaml` and `helm/cluster-issuer` (ACME solver via `http01.ingress`) are the source of truth now, not an open decision.
- Whether a Forgejo (or similar) Git server with Actions is warranted for the promotion-approval workflow: RESOLVED — yes. `jakob/kind-lab-argo-kargo-tekton` on the user's self-hosted Forgejo is set up as a GitHub pull-mirror (Forgejo periodically syncs `main` on its own; no manual dual-push), giving Tekton Pipelines-as-Code a push source to react to via webhook.
