Sub-project 5, Forgejo + Tekton Pipelines-as-Code, is complete and working. Tekton Pipelines v1.16.0 and Pipelines-as-Code (PAC) v0.51.0 install via ArgoCD from vendored upstream manifests (`gitops/apps/tekton-pipelines.yaml`, `gitops/apps/pipelines-as-code.yaml`, `vendor/tekton-pipelines/`, `vendor/pipelines-as-code/`); `scripts/pac-forgejo-secret-up.sh` and `scripts/forgejo-repo-up.sh` create the `pac-forgejo-creds` Secret (webhook shared secret + PAT) and register the repo (`jakob/kind-lab`) and webhook against the user's self-hosted Forgejo mirror at `https://git.local`; `https://pipelines-as-code.lab.test` is exposed on the shared Gateway with a trusted cert plus a PAC `Repository` CR via `helm/pipelines-as-code-config`/`gitops/apps-templates/pipelines-as-code-config.yaml.tmpl`/`scripts/pac-config-up.sh`; and a minimal proof-of-concept pipeline lives at `.tekton/pipelinerun.yaml`, auto-discovered by PAC. End-to-end verification (a real `git push`, not a synthetic webhook redelivery, which proved unreliable for exercising the pipeline-matching path) surfaced four real, previously-undiscovered environmental bugs, each only reachable after fixing the one before it: (1) `cloud-provider-kind`'s Gateway LoadBalancer IP is bound to the Mac's loopback interface, unreachable from any other LAN device including the Raspberry Pi running Forgejo — fixed with a `socat` TCP forwarder run as a root LaunchDaemon on the Mac (`scripts/pac-lan-forward-up.sh`, forwarding the Mac's real LAN IP:443 to the Gateway) plus a hosts override inside the Forgejo container; (2) Forgejo didn't trust the step-ca root that signs `pipelines-as-code.lab.test`'s cert, failing its outbound webhook TLS handshake; (3) Forgejo's `webhook.ALLOWED_HOST_LIST` silently drops webhook deliveries to private IPs by default — the API always returned 204 while the PAC controller saw nothing, with the rejection logged only in Forgejo's own container logs; both (2) and (3) fixed via `scripts/pac-forgejo-trust-up.sh` (step-ca root installed into the Forgejo container's trust store; `ALLOWED_HOST_LIST` added to `app.ini`); and (4) the mirror image of (2) — PAC's distroless controller and watcher containers, with no OS trust store, failed calling back into `https://git.local` (fronted by Caddy, which issues a cert from its own local CA, distinct from step-ca) to fetch the pipeline definition and post commit statuses — fixed with a `pac-controller-ca-bundle` ConfigMap (Forgejo's base CA bundle plus Caddy's local root) mounted into both Deployments with `SSL_CERT_FILE` pointing at it, built by `scripts/pac-ca-trust-up.sh` and requiring a direct edit to the vendored `vendor/pipelines-as-code/release.yaml` to add the volume/volumeMount/env. Bugs 2-4's fixes are idempotent and wired into `bootstrap.sh` (`pac-forgejo-trust-up.sh`, `pac-ca-trust-up.sh`); bug 1's fix (`pac-lan-forward-up.sh`) is standalone and run by hand, not wired into `bootstrap.sh` — but it is NOT a run-once-ever step: the LaunchDaemon itself persists across reboots, but its forwarding target (the Gateway's `cloud-provider-kind` LoadBalancer IP) is reassigned on every cluster rebuild, so the script must be re-run after every `cluster:up` (or any other event that changes that IP or the Mac's LAN IP) for LAN-delivered webhooks to keep reaching the cluster. Verified via a real `git commit --allow-empty` + `git push forgejo main`, triggering a genuine webhook that the PAC controller matched and resolved against `.tekton/pipelinerun.yaml`, creating `PipelineRun kind-lab-pac-poc-5s5xd`, which reached `Succeeded` (pod logs: "pac says hi from ..." / "triggered by PAC on kind-lab"), with PAC's watcher posting the final status back to Forgejo so the commit shows `Pipelines as Code CI / kind-lab-pac-poc- : success`. This was verified against the existing running cluster, not a full `cluster:down`/`cluster:up` cold rebuild — the same lighter bar sub-project 3a's paragraph above notes for itself. One remaining fragility: mid-troubleshooting, the Raspberry Pi's Forgejo container was switched from dynamic to static Docker port publishing (`-p 3000:3000 -p 2222:22`) so it would stop breaking the user's own Caddy reverse-proxy config on every container recreation — a necessary fix, but now a fact about the Pi's setup that this repo doesn't manage (it only reaches the Pi via SSH for the two `pac-*-trust-up.sh` scripts). `.github/workflows/ci.yml` and the Kargo promotion sub-project's decision against using Forgejo for promotion approval are both untouched by this work.

## Intent (from README.md)

This is a Kubernetes platform engineering lab built around a local `kind` cluster, managed via `task` (Taskfile.yaml) and bootstrap scripts (bash, invoked from the Taskfile).

- **Cluster**: `kind`; cluster infra images are `kind load`'ed, but demo-app images are pulled from a private `ghcr.io` registry (see Sub-project 3a below) — the local Docker registry container this line originally referred to was removed.
- **TLS**: cert-manager issues certs cluster-wide from an intermediate CA issued by a local `step ca` (already trusted by the macOS system trust store). Ingress is decided: Cilium's Gateway API implementation, with cert-manager solving ACME HTTP-01 challenges through it — traffic is real HTTPS end-to-end, not HTTP only.
- **GitOps**: ArgoCD, App-of-Apps pattern, manifests/charts sourced from this repo.
- **Promotion**: Kargo promotes a Go app release from dev to a "prod" lab environment, with a dashboard. Open question to evaluate: whether a Git server with Actions (Forgejo) is needed so developers can PR and request promotions, with approval-gated automation and app tests.
- **Observability**: Datadog Operator deploys the Cluster Agent. Uses the EU site (`https://app.datadoghq.eu`) and the local `DATADOG_API_KEY` env var — the cluster is free to use this key directly. A Datadog MCP server is also configured for Claude's own use (separate from the cluster's key).
- **Demo app**: a Go service generating continuous low-level dummy load, with high load triggerable via its web UI or API, writing data into Clickhouse.
- **Clickhouse**: vendored chart with a custom lab-scoped `values.yaml`.

A single templated chart, `helm/gateway`, owns `lab-gateway`'s full `spec.listeners` (a `kubectl apply` on a Gateway replaces the whole array, so this needs to stay a single source of truth rather than additive patches). `helm/gateway/templates/gateway.yaml` renders one HTTP+HTTPS listener pair per app from a `listeners` values list, so onboarding a new app is now a one-line values append instead of a listener-ownership conflict.
